# 即売会向けPOSレジスター 要件定義

- 文書版: v0.5
- 更新日: 2026年7月24日
- 変更元: v0.4
- 主な更新: 2026年7月24日までにAcceptedとなったADR-P004/P005、ADR-D007〜D020を統合
- 対象: 即売会で使用するローカルWeb型POS
- 対象プリンター: EPSON TM-T70II（58 mm仕様）
- 印字言語: 日本語

## 1. 目的

本システムは、同人誌・グッズ等の即売会で、複数の販売担当者が同時に会計し、売上、在庫、年齢確認、レシート印刷、現金管理およびレジ締めを一元処理するPOSである。

会場内の専用Wi-Fi LANで動作し、レジ端末、顧客画面および管理端末はWebブラウザーから接続する。インターネット接続、クラウドサービスおよびDiscord botは、通常の販売業務と印刷に必要としない。

## 2. 要件の要約

| 項目 | 要件 |
| --- | --- |
| 最大レジ数 | 基本4台 |
| 最大顧客画面数 | 4台 |
| 最大同時接続数 | 約10接続（レジ4、顧客画面4、管理端末2） |
| 会計処理量 | 通常10件/分、最大60件/分 |
| 本番サーバー | 即売会へ持ち込むWindows PC |
| 業務コード | Windows/Linuxで共通。OS固有処理はprinter portとservice管理に限定 |
| 操作端末 | iPad横画面およびPC横ウィンドウを優先 |
| 本番通信 | ローカルCAによるHTTPS |
| プリンター | EPSON TM-T70IIを1台共有 |
| プリンター接続 | Windowsで実測後にADR-P001で確定 |
| 内部ID | UUIDv7 |
| 受付番号 | 取引・取り置き共通の `SNNN-NNNC` |
| 商品・価格・在庫 | event別 |
| 頒布価格 | 税込 |
| 任意値引き | 初期上限100%。承認・理由入力は当面実装しない |
| 無料配布 | 売上に含めず在庫移動として記録。理由入力は当面実装しない |
| 返品 | 全部返品、またはレシートなしの商品コード返品 |
| 見本 | 専用在庫区分を設けず販売可能在庫として扱う |
| データ削除 | アプリケーションから行わない |
| 会計出力 | 製品非依存のcanonical export bundle |

## 3. システム構成

### 3.1 基本構成

単一のPOSサーバー、単一SQLiteデータベース、単一印刷ワーカーを基本とする。POSサーバーはWeb画面、認証、商品、在庫、取引、支払、監査、端末同期、印刷キュー、CSV出力およびバックアップを一元管理する。

各ブラウザー端末からプリンターへ直接印刷してはならない。印刷依頼はサーバー上の永続キューへ登録し、1件ずつ直列処理する。

### 3.2 端末

| 端末 | 主な機能 |
| --- | --- |
| レジ端末 | 商品登録、会計、取消、返品、再印刷、担当者ログオン |
| 顧客画面 | 商品、数量、単価、小計、合計、R18確認、会計状態の表示 |
| 管理端末 | 商品・在庫・event設定、責任者操作、締め、export、復旧 |

顧客画面は特定のレジへ割り当てる。顧客画面がなくても会計できる。切断はレジへ警告し、顧客操作を必要としない会計は継続できる。

### 3.3 OSとハードウェア

本番サーバー兼プリンターホストはWindows PCとする。業務ロジック、データベース構造、Web UIおよび自動試験はWindows/Linuxで共通とし、OS固有処理を`PrinterTransport`とservice管理の外へ漏らさない。

現在TM-T70IIが接続されているDebian上の`discord-printer-bot`は比較基準であり、本製品のsubmodule、package依存または実行時依存にしない。移植コードは移植元commitとファイルを記録し、このリポジトリへ試験とともに取り込む。

本番Windows PC、router、UPS、予備機材、復旧時間目標はADR-P006の実機・運用証拠により確定する。

## 4. 性能・同時実行

- 最大10端末を同時接続できる。
- 60会計/分を処理し、取引、支払、在庫移動および印刷operationに欠落・重複を生じさせない。
- 会計確定と初回印刷operation登録を同じDB transactionで行い、USB送信はcommit後に行う。
- 同じ確定要求の再送、Enter連打およびボタン連打でも取引を一度だけ確定する。
- 最後の1点を複数レジが同時販売した場合も全取引を記録し、在庫を追記型movementで整合させる。負数時は関係取引を含めて警告する。
- 会計確定と印刷完了を分離し、画面上でも区別する。

## 5. 認証・権限・責任者承認

### 5.1 スタッフ

スタッフは内部IDで管理する。event別にASCII数字3桁の責任者番号を有効期間付きで割り当て、同時期の重複を拒否する。ログオン用バーコード、責任者番号、暗証番号を使用できる。

取引、取消、返品、値引き、在庫調整、R18確認、再印刷および締めに実行者を記録する。PIN、session tokenおよび身分証情報をログへ保存しない。

### 5.2 権限

| 権限 | 主な操作 |
| --- | --- |
| 販売担当者 | 通常会計、未確定取引の取消、売上・在庫の閲覧 |
| 責任者 | 返品、確定済み取引の取消、在庫調整、再印刷、締め |
| システム管理者 | event・スタッフ設定、データ出力、復旧 |

管理操作の承認には実行者、承認者、対象、日時、端末、理由を保存する。同一人物による自己承認はevent設定で許可でき、`self_approved`とrisk acceptanceを監査する。

### 5.3 レシートの担当者表記

event設定で責任者番号または登録表示名の一方を選ぶ。初期値は責任者番号とする。表示名はペンネームまたはハンドルネームを許可し、法的氏名を要求しない。取引snapshotへ印字文字列を保存する。

## 6. 商品・価格・在庫

### 6.1 event別商品

商品コード、名称、税込価格、税率・税区分、原価、販売状態および在庫はevent別とする。同じ商品コードを別eventで再利用でき、同一event内では一意とする。過去取引には取引時点の値をsnapshot保存する。

商品管理コードは数字のみ8桁以上とし、UI、CSVおよびAPIで共通検証する。先頭ゼロを保持し文字列として扱う。ただしscanner identityとは分離し、商品へ複数の外部barcodeを関連付けられるようにする。

### 6.2 在庫

開始、追加入庫、販売、取消・返品、破損・廃棄、無料配布、取り置きおよび手動調整を追記型movementとして記録する。確定済みmovementを上書き・削除せず、訂正は逆方向movementを追加する。

見本専用の在庫区分、movement、画面およびCSVは設けない。展示に使った商品も販売可能在庫として通常販売し、汚損時だけ破損・廃棄movementを使用する。

### 6.3 セット販売

セットは構成商品と数量を一括登録する、在庫を持たない版付きショートカットとする。売上、税および在庫は構成商品へ記録する。構成の一部が登録不能なら全件を失敗させ、部分登録を残さない。

### 6.4 自動値引き

値引きルールは対象商品、必要数量、値引額または率、適用上限、priorityおよび有効期間を持つ。同一の商品数量tokenを複数ルールへ重複割当てしない。

率値引きは割当て前税込金額へ1回だけ適用する。全候補から最終支払額が最小の組合せを選び、同額の場合はpriority、rule ID順で決定する。適用結果と整数円の行別配賦をsnapshot保存する。

### 6.5 任意値引き

初期版は率上限100%とし、取引合計0円まで許可するが負数は禁止する。責任者承認機能と理由入力機能は当面実装しない。将来拡張用の未使用UIを作らない。

### 6.6 無料配布

無料配布は売上、0円売上または値引販売ではなく独立した在庫移動とする。商品、数量、日時、担当者、eventおよび原価snapshotを保存し、売上、支払および税率別売上に含めない。理由入力機能と理由masterは当面実装しない。

購入取引に紐づく無料配布では、可能なら顧客画面の対象行を短時間0円表示にする。初期版では待機表示の継続を許容する。会計外の無料配布では内部情報を顧客画面へ送らない。

### 6.7 取り置き

取り置きは販売可能数量から予約数量を除外する。登録、受取、解除を履歴として追記し、会計確定時に販売へ移す。未解決分は締めで一覧、件数および数量をsnapshot保存する。

販売可能数量を超える取り置きは、不足数と作成後数量を警告し、担当者が明示続行した場合に許可する。自動補正せず、負数と関連する取り置きIDを監査・締め警告へ残す。

## 7. 会計・支払

### 7.1 基本フロー

担当者ログオン、商品登録、値引き計算、R18確認、支払登録、会計確定、初回印刷operation登録、顧客画面clearの順とする。

会計確定時に取引、明細、値引配賦、税、支払、R18参照、承認、在庫、現金台帳、監査および初回印刷operationを一つのDB transactionへ含める。

### 7.2 支払

現金、外部決済および併用払いを扱う。外部決済端末とは直接接続せず、担当者が結果と金額を記録する。支払合計が取引合計と一致するまで確定しない。外部決済の結果をPOSが推測しない。

釣り銭計算省略モードでは受取額・釣り銭を未入力とし、売上額だけを現金台帳へ加算する。現金預り金不足時は取引および現金支払明細を作成しない。

## 8. 受付番号・バーコード入力

### 8.1 共通受付番号

取引と取り置きは共通counterを使う。内部IDはUUIDv7とし、人間向け受付番号を検索用alternate keyとして分離する。

受付番号本体はevent内営業セッション番号1桁`S`とbusiness day内全レジ共通連番6桁`NNNNNN`からなる。Damm検査数字`C`を付け、通常表示を`SNNN-NNNC`、完全表記を`YY-MMDD-SNNN-NNNC`とする。

真の新規開局では`S`を進め、連番を`000001`へ戻す。締め取消・再開は同じbusiness dayと`S`の続番を使う。欠番を許容し、取消後も番号を再利用しない。`S=1..9`、連番`000001..999999`とし、上限で循環させない。

### 8.2 barcode名前空間

外部EAN、UPC、ISBN、ISDNおよびインストアコードの数字領域を商品用途へ開放し、POS内部用の数字領域を予約しない。278、279、292を内部用途へ使用しない。

システム用barcodeは非GS1 Code 128とし、`PS11`を取引、`PS12`を取り置き、`PS13`を内部商品とする。後続にはDB一意制約を持つscanner専用tokenを使用し、DB参照の正本はUUIDv7とする。

scanner入力は共通`BarcodeRouter`へ渡す。`PS`で始まる不正値を商品や金額へfallbackしない。数字だけのGTIN候補はcheck digitを検証する。scanner入力と現金入力を別bufferにする。

通常の商品登録画面では、登録済みbarcodeまたは8桁以上の商品管理コードを商品として扱い、1〜7桁を現金預り金として扱う。支払画面では選択中の支払方法の金額として扱い、商品へ読み替えない。

## 9. 税

レジ、顧客画面およびレシートの頒布価格は税込とする。消費税額はレシート全体を税率別に集計し、各税率につき1回だけ丸める。

初期方式は切捨てとし、切捨て・四捨五入・切上げを設定できる。営業中は変更せず、締め後に予約して次営業から適用する。

取引共通値引きは値引前税込金額比で配賦し、端数は最大剰余法により小数部、税率、行番号の順で決定的に配る。返品は元snapshotを反転し、現在の価格・税率で再計算しない。

## 10. R18頒布・年齢確認

event初期policyは担当者による容貌確認とする。自己申告は補助であり、省略可能かつ容貌確認または身分証目視の代替にしない。

保存するのは確認方式、結果、確認者、取引および日時だけとする。身分証の種類、番号、氏名、住所、生年月日および画像をDB、ログ、CSV、レシート、backupへ保存しない。

確認不能時はR18商品だけをdraftから外し、他商品は会計を継続できる。確認条件を満たした後で再登録できる。

## 11. 顧客画面

商品名、数量、税込単価、小計、値引き、合計、R18確認および会計状態を表示する。顧客画面から商品、数量、価格または支払を変更できない。

取引終了後は商品名、金額および確認結果を消去して待機画面へ戻す。内部理由、担当者情報、PINおよびsession情報を送信しない。

## 12. プリンター

TM-T70IIの58 mm仕様、最大416 dotを物理上限、384 dotを標準内容幅とする。論理レシートは宣言的template、型付きAST、canonical IR、ESC/POS bytesの順に生成し、取引差込み文字列をcommandとして解釈しない。

同じsnapshot、template、asset、font、rendererおよびfinishing policy版から同じIR/bytesを再現する。初回印刷と再印刷を別operationとし、再印刷で売上を再計上しない。

プリンター状態を推測しない。取得不能は`unknown`とする。送信開始後に結果不明となったoperationは自動再送せず、人間が紙面を確認して明示的に再印刷する。

Windowsの送信方式、状態能力、排他、再接続および部分カットはADR-P001/P002の実測後に確定する。Debianの既存出力は比較基準であり、本番対応OSには含めない。

キャッシュドロアーはレシートtemplateから分離した専用device operationとする。型番、pin、pulse、安全制限をADR-P003で確定するまで実機駆動しない。

Windows実機試験の前に、Debian側Discord bot serviceの停止とUSBが使用中でないことを明示的に確認し、USBをWindowsへつなぎ替える。driver、USB device、送信bytes、raw response、ログおよび紙面結果を保存する。

## 13. 取消・返品・返金

確定済み取引を上書き・削除せず、元取引を参照する反転記録を追加する。元レシートに対する部分返品は実装しない。

返品は元取引の全商品・全支払を反転する全部返品とし、残す商品は新規取引として再登録する。レシートなし返品は商品コード、数量、返金方法、担当者および理由を持つ独立返品として記録できる。

累積返金が販売数量・支払額を超えないようDB transaction内で防ぐ。外部決済端末の結果は`completed/failed/unknown`として記録し、推測しない。

## 14. 現金管理・締め

レジ別現金箱と共通現金箱を扱う。営業中のモード変更を禁止し、締め後に予約して次business dayから適用する。各business dayへ使用モードをsnapshot保存する。

現金の正本は追記型cash ledgerとする。金種別入力は行わず、準備金と実在高を総額入力する。

```text
理論現金 = 準備金 + 現金売上 - 現金返品 - 出金 + 入金
現金過不足 = 実在高 - 理論現金
```

締めでは未完了取引、印刷operation、取消・返品、現金、在庫、支払別・担当者別売上、未解決取り置きを確認する。部分締めは実装しない。締め取消・再開は責任者承認と理由を必要とし、元締めを変更しない。

## 15. データ保存・export・復旧

売上、在庫、現金および監査記録は追記型とし、アプリ内の自動削除、行単位削除および匿名化を実装しない。

event終了時にDB、CSV、manifestおよびhashを暗号化archiveへ固定する。保持年数は運用側がeventへ設定する。期限処理は停止、backup、対象確認、責任者承認、削除、証跡保存を含む保守runbookで行う。

特定会計ソフトへ依存しないcanonical export bundleをevent、business dayまたは日時範囲で随時生成できる。同じschema version、範囲およびDB状態から同じ業務データを再生成でき、正本DBへ出力済みフラグを書かない。

bundleはUTF-8 BOM付きRFC 4180 CSV群と`manifest.json`で構成する。取引、明細、値引配賦、税率別集計、支払、返品・取消、在庫移動、無料配布、取り置き、現金台帳および締めを含め、各CSVに内部UUIDとevent IDを持たせる。manifestにはschema version、export ID、範囲、生成日時、行数およびSHA-256を保存する。

会計ソフト固有adapterは初期実装しない。採用製品が決まった時点で変換adapterとgolden testを追加する。

## 16. 通信・セキュリティ

本番はローカルCAで署名したHTTPSを使用する。固定hostnameと必要なIPを証明書SANへ含める。端末導入手順にCA配布、明示的信頼、fingerprint確認、接続試験および紛失時解除を含める。

cookieは`Secure`、`HttpOnly`、`SameSite=Strict`とし、Origin検査、CSRF token、短いsession期限、端末pairing、secret redactionを併用する。

HTTPはloopback開発だけを既定許可とする。隔離LANでの一時検証には明示したrisk acceptanceと当日限りの資格情報を必要とする。

## 17. 操作性

iPad横画面、PC横ウィンドウ、スマートフォンの順に最適化する。主要操作はタッチ、マウスおよびキーボードで行えるようにし、Enterの意味を画面状態ごとに一意にする。

警告は色や音だけに依存させない。十分なコントラスト、可視フォーカス、十分なタッチ領域、拡大時の主要操作維持を満たす。

## 18. 障害対応

- プリンター障害時も会計確定と印刷結果を分離して表示する。
- レジ切断時は結果を推測せず、再接続後に冪等keyまたは取引IDで照会する。
- サーバー再起動後にDBと永続印刷キューを復元する。
- 顧客画面切断、router障害、停電、Windows自動更新、sleepおよびUSB省電力への運用手順を用意する。
- 実機状態を取得できない場合は正常・異常へ読み替えず`unknown`とする。

## 19. 監査

ログオン、会計、取消・返品、値引き、在庫調整、無料配布、取り置き、R18確認、承認、ドロアー、再印刷、設定変更、締め・再開およびexportを監査する。

日時、実行者、承認者、端末、操作、対象ID、canonicalな変更前後snapshot、理由および自己承認を記録する。秘密情報と身分証情報を除外し、監査ログの編集・削除機能を設けない。

## 20. 受入条件

受入条件は`docs/design/04_test-strategy-and-acceptance.md`の46件（AC-01〜22、PR-01〜11、R18-01〜03、CL-01〜10）を正本とする。

自動試験だけで実機・人間確認を完了扱いにしない。各結果へcommit、環境、入力、期待値、実測値、ログ、画面、紙面または動画、および判定者を紐付ける。

| P001 | Windowsのdriver、RAW/USB方式、timeout、排他、再接続 | 本番PrinterTransport、PR-01〜04/06/07 |
| P002 | 接続、online、cover、paper、errorの取得能力 | 正式状態監視、PR-03/04 |
| P003 | drawer型番、pin、pulse、安全制限 | 実機drawer、PR-06 |
| P006 | 本番Windows PC、router、UPS、予備機、復旧目標 | 総合性能・障害訓練、CL-10最終受入 |

未確定値を仮の本番既定値で埋めない。P001/P002はWindows PCとTM-T70IIの実測結果、P003は製品仕様と安全な実機結果、P006はBOMと本番相当訓練を保存してから決定する。

Code 128のmodule幅、高さ、quiet zoneおよび連続100回読取りは、使用予定scannerと58 mm実機で確定する。
