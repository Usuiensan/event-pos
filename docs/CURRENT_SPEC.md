# ぽすりん 現行仕様

この文書は、現在の実装を説明するための正本です。開発途中の構想や過去のGoalを将来要件として保存する目的ではありません。

## 1. 正本の優先順位

実装と文書が食い違う場合は、現在のコード、DB schema、自動テストを確認し、この文書を実装へ合わせます。

新しい必須要件は、次のいずれかに限ります。

- ユーザーが明示して追加したもの
- 会計の整合性またはデータ損失防止に必要なもの
- 実際に採用する構成で安全に動かすために必要なもの
- 明確なセキュリティ上の必要性があるもの

開発時に提案された性能値、対応OSの同格化、特定のテストツール、証跡数などを、それだけを理由に必須要件へしません。

## 2. 製品範囲

即売会で商品を頒布するための複数端末対応Web POSです。

基本構成は次のとおりです。

- POS server 1台
- SQLite 1データベースを業務データの正本とする
- ブラウザーのレジ画面、顧客画面、管理画面
- 必要に応じてEPSON TM-T70IIとPrinterHost

イベントごとに実際に使うOS、PC、端末台数を選びます。WindowsとLinuxの双方を同時に本番受入することは製品共通の完了条件ではありません。

## 3. 現在実装されている業務

### 商品・設定

- event単位の商品、価格、税区分、販売状態、担当者、画面設定
- 分割YAMLを人が編集する設定の正本として利用可能
- 従来のEventCatalog JSONインポート/APIも互換経路として維持
- 商品タブ、クイック登録、自動値引き
- JAN/EAN/UPC、ISBN、ISDN等の入力補助
- 未登録JANの仮商品登録

### 販売

- SQLiteへ永続化したsale draft
- draft versionによる競合検出
- Idempotency-Keyによる会計確定の重複防止
- サーバー側での価格、値引き、税、支払再計算
- 現金、クレジット記録、売掛、無配
- 現金の預り金と釣銭
- 支払いは複数行に分けて登録でき、支払い画面に登録済みの内訳と残額を表示する。登録済みの支払い行は会計確定前に取り消せる。支払い合計が会計金額を超える登録は受け付けない
- 取引受付番号と内部UUIDv7。受付番号は10桁（営業セッション番号2桁＋連番7桁＋Damm検査数字1桁）で、表示は5桁-5桁。営業セッション番号は1〜99。旧形式の8桁（営業1桁＋連番6桁＋検査数字）の受付番号も、発行済みレシートの検証・スキャン判定のため引き続き受理する。レシートのバーコードは営業日6桁＋受付番号（旧8桁または現行10桁）のITF

レジの完了画面は、再接続後も確定時の商品名・単価・値引き・合計・支払金額を表示します。保留から呼び戻した会計も、確定した取引のお釣り（現金の場合）と受付番号を表示し、その取引の領収書を発行できます。

会計確定では、取引、明細、支払、税、在庫移動、現金台帳、監査、初回印刷job等を同じSQLite transaction内で確定します。途中失敗時に一部だけ残さないことを重要な不変条件とします。

### 在庫・取り置き

- inventory movementを記録し、残数を投影
- カタログの再取込では、取込対象商品の期首数量に同じイベント・商品の在庫移動の合計を足し、在庫投影を更新する。既存の引当数は保持する。棚卸しで確認した実数は、理由付きの在庫調整で反映する
- マイナス在庫を許可
- 取り置き作成、予約数反映、受取会計、解除に対応
- 翌営業への繰越予約は1回限り。繰越済みの取り置きへの再度の予約は 409 で拒否し、受取または解除が必要
- 受取会計に取り込んだ取り置きは、会計の編集中や保留中も引当を維持する。会計を中止すると取り置きは有効に戻る
- 受取会計を確定すると、取り込んだ取り置きの引当を全数解除し、販売した数量だけ実在庫を減らす。数量を減らしたり明細を取り消したりした分も引当を解除する
- 受取会計の明細をすべて取り消しても、会計を解決するまではレジの精算・営業の閉局ができない
- 運用ダッシュボードの閉局阻害一覧には、会計の明細数にかかわらず、対象営業日の未確定の受取会計に取り込まれた取り置きも表示する
- 営業中でも manager 以上が理由付きで現在庫数を調整できる（adjustment movement と監査へ記録）

在庫数の入力差異だけを理由に販売会計を停止させる設計にはしません。

### 年齢確認

- 年齢要件は商品の ageCheck のみで決まり、商品名からの推定はしない（ageCheck 未指定の商品は年齢確認不要）
- 18歳以上、20歳以上の確認
- 容貌確認、身分証目視等の確認方法と結果を記録
- サーバーでの会計確定には、商品が求める年齢以上の担当者確認のうち、登録順で最後の結果が合格であることが必要（20歳の確認は18歳の要件も満たす）
- 身分証番号、生年月日、氏名等の身分証個別情報は保存しない
- 顧客画面を使う確認経路にも対応
- 顧客画面での確認または客側スキップの後、店員が身分証を目視して「確認できた」を押すと商品を登録する

### 顧客画面・同期

- レジごとのpublic projection
- WebSocketによる更新通知
- RESTによる状態再取得
- 顧客画面heartbeatによる利用可否判定
- 会計を保留すると顧客画面に保留後の状態を反映し、呼び戻すと復元した明細と合計を表示する
- 会計を登録中止すると顧客画面の明細と値引きが消え、合計が 0 円になる
- 登録中止と同じトランザクションで、その会計の未応答・応答済みの年齢確認要求を取り消し、顧客画面は次の状態取得時に案内を消す

WebSocket接続そのものを業務データの正本にはしません。再読込や再接続後はSQLite上の状態から復元します。

### レシート・印刷

- ReceiptSnapshotを会計確定時に保存
- ESC/POS bytesとhashを永続化
- EPSON TM-T70II向けPrinterHost
- 永続FIFO印刷キュー
- 再印刷
- Windows/Linux用PrinterHost実装と実機証跡を保持

実際の本番対応可否は、イベントで採用するOS・PC・接続方式で確認します。全対応OSを同時に検証する必要はありません。

印刷送信開始後に結果が不明になった場合は自動再送しません。紙が出た可能性があるため、売上を再確定せず、既存取引の印刷状態を確認して必要なら明示的に再印刷します。

Linux RAWで途中まで送信した場合は、確認できた受理バイト数を印刷試行に記録し、ジョブを結果不明の失敗として扱います。

紙切れやカバー開、オフラインなど、実測できた異常で送信前に止まった場合は印刷キューが停止します。カバー開と用紙切れはレジ画面にもアラートを表示します。障害を解消したら、管理画面のプリンター・印刷キューで責任者が「印刷を再開」します。再開するとPrinterHostは先頭ジョブの再要求でプリンターの状態を読み直し、送信可能ならキューの順に印刷します。障害が続いていればキューは再び停止します。

プリンターの状態が未確認（unknown）なだけで送信できなかった場合は、機器障害としてキューを止めず、通常のバックオフで自動再試行します。

プリンター状態APIはドロアーの有効可否（drawerEnabled）も返します。レジ画面はドロアーが無効な環境では「ドロアーを開く」ボタンを表示しません。ドロアー駆動の運用上の拒否（DRAWER_NOT_ACCEPTED等）はシステムエラーではなく操作エラーとして表示します。

PrinterHostにPRINTER_HOST_TOKENを設定した場合は、サーバーも同じトークン（環境変数PRINTER_HOST_TOKEN）で認証します。USBキットではprinter-host.env／printer-host-macos.envのトークンをサーバーワーカーへも渡します。認証が失敗した（401）ジョブはPrinterHostへ届いていないため、結果不明ではなく「未送信」の失敗として記録します。

### 現金・営業

- 営業開始、レジ準備
- 金種別準備金
- 売上以外の入金・出金
- 理論現金、実在高、過不足
- 中間点検、精算、再開

明細も支払もない下書きが残っていても精算・閉局できます。次の営業で商品登録を始めると、その営業のレジ用に新しい下書きを作ります。

下書きは営業セッション単位で管理します。別のイベントの営業へ切り替えても、旧セッションの未確定下書きは残ったまま、新しいセッションの下書きを作れます。旧セッションに戻れば、その下書きが再び表示されます。

中間点検・精算・入出金の冪等キーは操作内容の単位で管理します。サーバー確定後の応答喪失に備えてキーと内容を対で端末に保持し、同じ内容の再試行では同じキーで記録済みの結果を受け取り、内容が変わった再試行では新しいキーを採番します（古いキーとの内容不一致で操作が詰まることはありません）。キーの保存枠は操作内容ごとに分け、別の操作（別タブ含む）が保留中のキーを上書き・削除しません。保存が成功した時点で操作は完了であり、その後の集計取得や再読込が失敗しても保存は再試行せず、表示の更新だけを案内します。入出金の冪等照合はセッション状態の確認より先に行い、精算後の再送でも記録済みの結果を返します。

運用ダッシュボードでは、同じ日に同じ現金箱を使って開局し直した場合も、開局・中間点検・精算の状況を現金セッションごとに表示します。

### 返品

- 元取引を指定した全部返品
- レシートなしの例外返品
- 例外返金で商品マスタに存在しない商品コードを入力したときは、操作者が確認した場合に限り、コードなし（在庫戻しなし）で登録できる
- 返品取引、在庫戻し、返金記録、監査、返品レシートを追記

部分返品専用処理はありません。必要な場合は全部返品後、残す商品を新規売上として登録する運用です。

### バックアップ・成果物

- SQLite snapshot
- xlsx
- manifest
- hashと成果物状態の記録
- 確定済み点検・精算からの成果物再生成

Excelは正本ではなく、SQLiteが正本です。

### LAN公開・接続案内

- USBキットのPOSサーバーは既定で `0.0.0.0:3000` で待ち受け、同じネットワークの他端末から接続できる。この端末のみ（`127.0.0.1:3000`）に制限する場合は、環境変数 `EVENT_POS_LAN=0`（または `false`）、もしくは起動引数 `--no-lan` を指定する（無効化の指定は有効化の指定より優先される）。環境変数 `EVENT_POS_LAN=1`（または `true`）と起動引数 `--lan` は有効化の指定として受理する（Windows は `start-usb-kit.ps1 -Lan` でも可。ランチャーの `.bat` / `.command` は引数をそのまま渡す）。
- LAN公開の対象はPOSサーバーだけ。printer-host は常に `127.0.0.1` のまま、練習環境（トレーニングサーバー）には適用しない。
- 管理画面に「接続案内」セクションがある。表示時点のサーバーがネットワークインターフェースから取得したLANアドレス（固定値ではない）と実際の待ち受けポートで、レジ画面（`?register=1&role=staff`）と顧客画面（`?register=1&role=customer`）のURLとQRコードを表示する。LAN未公開時はその旨と有効化方法を警告表示する。
- 接続案内にはWi-Fi接続QRも表示する。接続先Wi-Fi（スマートフォンのテザリング等）のSSIDとパスワードは管理画面で編集・保存でき、サーバーの `app_metadata`（キー `connection_wifi_ssid` / `connection_wifi_password`）に保持する。QRの元文字列は `WIFI:T:WPA;S:<ssid>;P:<password>;;` 形式（パスワード空欄時は `WIFI:T:nopass;S:<ssid>;;`、区切り文字はバックスラッシュでエスケープ）。保存時の監査ログにはパスワードを含めない。
- API は `GET /api/v1/connection-guide`（待ち受け情報・LANアドレス・URL・Wi-Fi設定を返す）と `PUT /api/v1/connection-guide/wifi`（Wi-Fi設定の保存）。どちらも責任者（manager）以上の権限が要る。SSIDは1〜32バイト、パスワードは空欄か8〜63文字。
- QRコードの生成はレジ画面のブラウザ内で完結し、外部通信は発生しない（バイトモード・誤り訂正レベルM・バージョン1〜10の自前実装。URLが長く収まらない場合は表示できない）。

## 4. 外部決済

クレジット等の外部決済端末とは自動連携しません。

外部端末側で決済成功を確認してからPOSへ支払を記録します。返品時も外部端末側の返金結果をPOSが自動取得・推測しません。

## 5. 現在の既知の制限

- 部分返品専用処理はない
- 外部決済端末との自動連携はない
- プリンターの紙面排出完了をOS受付だけから常に証明できるわけではない
- プリンターのpaper/cover等の状態取得能力はOS・driver・adapterで異なる
- 実際の会場ネットワーク、USB、プリンター個体、端末構成はイベントごとに確認が必要

これらを理由に、未使用機能や未採用OSまで本番必須検証へ広げません。
