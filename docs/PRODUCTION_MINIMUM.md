# 本番投入までに最低限確認すること

この文書は、event-posを実際の即売会で使う前に必要な確認だけを定めます。開発上の理想的な網羅試験を列挙する文書ではありません。

## 1. 本番可否の考え方

確認対象は、**実際のイベントで使う機能・OS・PC・ブラウザー・プリンター・端末台数**です。

次はプロジェクト共通の本番必須条件ではありません。

- WindowsとLinux双方を同時に受入すること
- 60会計/分、900件等の固定負荷値を達成すること
- 10端末を必ず接続すること
- Playwrightやk6など特定ツールで試験すること
- 全てのプリンターsensor/faultを自動判別すること
- ローカルCAを全構成で必須にすること
- 過去のGoalや受入台帳を全件消化すること

必要なのは、当日使う構成で会計を壊さず、通常運用と最低限の復旧ができることです。

## 2. 本番前に必ず確認する項目

### A. 対象commitが正常にbuild・testできる

本番へ持ち込むcommitで原則として次を通します。

```powershell
pnpm install --frozen-lockfile
pnpm check
```

文書だけの変更でコードに影響しない場合を除き、失敗した状態を本番版として固定しません。

### B. 当日のイベント設定が正しい

実際のevent設定で次を画面または生成結果から確認します。

- 商品名
- 頒布価格
- 税区分
- 販売対象商品
- 担当者
- 年齢確認が必要な商品
- レシートのevent名・サークル名等
- 当日使う値引きやクイック登録

YAMLを使う場合はvalidate/buildを通します。

### C. 実際に持ち込む構成で接続できる

- POS serverが起動する
- SQLite DBの保存先が意図した場所である
- 当日使うレジ端末からPOSへ接続できる
- 顧客画面を使う場合は、その端末でも表示・再接続できる
- 管理画面を使う端末から必要な操作ができる

端末数は固定しません。当日使う予定台数で同時に操作して問題がないことを確認します。

### D. プリンターを使う場合、実物で一連の動作を確認する

実際に持ち込むTM-T70II、PC、USBケーブル、driver/PrinterHost、58mm紙で次を確認します。

- 日本語と金額が正しく印字される
- 紙送りとカットが実用上問題ない
- 会計後にレシートが出る
- USB切断、紙切れ等の「印刷できない状態」を少なくとも一度作り、売上を再確定せずに復旧・再印刷できる

OSが印刷を受け付けたことと紙面が出たことが同じとは限りません。結果不明時に自動再送しない現在の設計は維持します。

プリンターを使わない運用なら、この項目は本番条件に含めません。

### E. 当日使う業務を最初から最後まで通す

実際に使う機能だけで通しリハーサルを行います。

最低限、現金を扱う場合は次を通します。

1. 営業開始
2. 準備金登録
3. 商品登録
4. 現金会計
5. 預り金・釣銭確認
6. 中間点検または精算
7. backup/xlsx/manifest生成

次の機能を当日使う場合だけ、その経路も1回確認します。

- クレジット等の外部決済記録
- R18/R20確認
- 取り置き
- 返品
- 顧客画面
- 再印刷
- 入金・出金

使わない機能の受入を本番条件にしません。

### F. バックアップを確認する

本番ではSQLiteを正本とします。成果物保存先を設定し、精算等から生成されたSQLite backup、xlsx、manifestが確認できることを確認します。

少なくとも一度、生成したbackup SQLiteを開けることと `PRAGMA integrity_check` が正常であることを確認します。

## 3. 負荷確認

固定の「60会計/分」「10端末」は要求しません。

当日の想定より少し多い程度の操作を、実際に使う端末数で数分続け、画面操作・会計確定・顧客表示・印刷が実用上詰まらないことを確認すれば最低限の本番確認とします。

大規模運用を予定する場合だけ、その規模に応じて負荷試験を増やします。

## 4. ネットワークとHTTPS

現在のDocker本番プロファイルはHTTPSを使用します。これを使う場合は証明書設定を行います。

別の構成で専用・隔離LANを使う場合まで、ローカルCA方式そのものを製品完成条件にはしません。ただし、来場者等と共有する信頼できないネットワークへ認証情報やPOS通信を平文で流す運用は避けます。

## 5. 本番を止める不具合

次のような問題が残る場合は本番投入を止めます。

- 同じ操作で二重売上が作られる
- 売上確定の一部だけがDBへ残る
- 金額計算が再現できない
- 確定済み売上が再起動後に消える
- 当日構成でPOSへ接続できない
- 使用予定プリンターで印刷できず、代替運用も決まっていない
- backupを作れず、売上正本を保全できない

一方、未使用機能の未完成、別OSの未検証、固定性能値の未測定、特定の自動E2Eがないことだけでは本番不可とはしません。

## 6. GO判定

次の状態なら、最低限の本番投入条件を満たしたものとして扱います。

- 当日使うcommitのbuild/testに重大な失敗がない
- 当日設定が確認済み
- 当日使う端末構成で通しリハーサル済み
- 使用する場合はTM-T70II実機印刷と復旧を確認済み
- 会計、精算、backupまで一連で成立する
- 会計データを壊す既知の重大不具合がない
